# PR 12 — Public Appointment Self-Service Implementation Contract

**Status:** Accepted — implementation authorized
**Implementation authorization:** Granted

### Approved implementation revisions

- A successful public reschedule returns the replacement management credential exactly once so the browser can continue the active management session. The credential remains memory-only; the frontend replaces the URL fragment with the rotated credential and removes it when the session ends.
- Public appointment DTOs do not expose the appointment UUID. Public routes use the opaque management credential as their authority and return only the human-readable appointment reference where identification is needed.
- New management credentials are issued only when both public self-service and appointment email are enabled. Disabling appointment email later does not invalidate an already-issued credential; disabling public self-service invalidates credentials immediately.
- Public management links retain the BookNowTech fallback hostname (`tenant-slug.booknowtech.com`) when no usable verified custom hostname exists.
- **Lost-link recovery** is a named future capability and is not implemented in PR 12.
- Business Hub displays a warning for very short self-service cutoff values so operators understand the customer-impact risk before saving.

**Estimated size:** One pull request, approximately 2–3 engineering days after approval

## 1. Objective

PR 12 adds secure, tenant-branded appointment self-service for customers who receive transactional appointment emails. A customer can use a private link to:

- view the appointment summary;
- see whether cancellation or rescheduling is allowed;
- browse valid replacement starts generated by the existing scheduling engine;
- reschedule the appointment; or
- cancel the appointment.

PR 12 does not create a customer account, customer portal, new scheduling engine, payment workflow, reminder system, or new infrastructure service.

## 2. Architectural invariants

PR 12 must preserve all accepted PR 2–11 patterns:

- Administrative authentication remains centralized and session-based.
- Administrative tenant context comes only from the verified selected membership.
- Public tenant context comes from the verified public hostname, never a client-supplied tenant ID.
- Appointment mutations reuse the PR 8 lifecycle, optimistic concurrency, schedule-lock, and conflict rules.
- Available starts reuse the PR 5–10 availability and scheduling engine.
- Appointment service, price, duration, buffer, timezone, and operational snapshots remain immutable during rescheduling.
- `local_start_date` remains server-derived and is recomputed after every reschedule.
- Transactional email continues through the PR 11 MongoDB outbox and existing Railway worker.
- Customers and appointments are tenant-scoped; no global customer identity is introduced.
- Raw bearer credentials must never be stored, logged, audited, or included in analytics.
- Invalid, expired, revoked, inactive, or cross-tenant resources use safe public `404` behavior.
- All lifecycle writes remain transactional, audited, idempotent, and reversible through deployment rollback.

## 3. Approved design recommendation

Use a purpose-bound opaque appointment access credential backed by a new tenant-scoped token record.

The credential is not a customer session. It grants narrowly scoped access to one appointment and only the actions explicitly allowed by the appointment and tenant policy.

### 3.1 Credential purpose

PR 12 supports one purpose:

```text
appointment_manage
```

The credential cannot authenticate a customer, access other appointments, modify customer data, change the service or provider, or call Business Hub APIs.

### 3.2 Raw-token derivation and hash-only persistence

Email delivery is asynchronous, so the API and worker must be able to construct the same link without persisting the raw bearer token.

Use a versioned deterministic derivation:

```text
raw_token = base64url(
  HMAC-SHA256(
    PUBLIC_APPOINTMENT_TOKEN_SECRET,
    canonical(version, token_public_id, appointment_public_id, generation, purpose)
  )
)
```

Persist only `SHA-256(raw_token)` as `token_hash`. Both the API and worker may derive the raw token from immutable record fields and the shared secret. The raw token must never be written to MongoDB, application logs, audit metadata, request logs, or notification template data.

Comparison of a presented token and the stored hash must use constant-time comparison.

Changing the derivation format requires a reviewed version change. Rotating the shared secret requires a planned operational migration because existing links will become invalid.

### 3.3 Public link format

```text
https://<active-public-host>/appointments/manage/<token_public_id>#token=<raw_token>
```

The raw token is placed in the URL fragment so it is not sent in the initial HTTP request, proxy logs, or referrer headers. The frontend reads it into memory and sends it only in:

```http
Authorization: AppointmentToken <raw_token>
```

The frontend must not place the raw token in a query parameter, request body, cookie, local storage, session storage, analytics event, error report, or DOM text.

The management route must emit `Referrer-Policy: no-referrer`, `Cache-Control: no-store`, and the existing restrictive content-security policy. It must not load third-party analytics or advertising scripts.

## 4. Token lifecycle

- At most one active `appointment_manage` token may exist for an appointment.
- A token is issued when an eligible appointment is created.
- Confirmation and rescheduling emails may include the currently active link.
- A successful reschedule consumes the old token and atomically issues a replacement token.
- A successful cancellation consumes the token and issues no replacement.
- A token expires at the appointment start, capped at 180 days after issuance.
- A replacement token receives a newly calculated expiry based on the new appointment start.
- Disabling tenant self-service immediately makes every token for that tenant unusable without deleting records.
- Cancelled, completed, and no-show appointments cannot be mutated through a token.
- Old or replayed tokens receive the same safe `404` response as unknown tokens.

Token records remain after consumption for operational evidence and retry reconciliation, then become TTL-eligible.

## 5. Data model

### 5.1 New `appointment_public_access_tokens` collection

```text
_id                         ObjectId
public_id                   UUID string
tenant_id                   ObjectId
tenant_public_id            UUID string
appointment_id              ObjectId
appointment_public_id       UUID string
purpose                     "appointment_manage"
generation                  positive integer
token_hash                  lowercase SHA-256 hex
status                      active | consumed | revoked | expired
issued_at                   Date
expires_at                  Date
consumed_at                 Date | null
revoked_at                  Date | null
created_at                  Date
updated_at                  Date
purge_at                    Date
mutation                    object | null
```

Optional `mutation` is retained only for safe request replay:

```text
type                         reschedule | cancel
idempotency_key_hash         lowercase SHA-256 hex
request_fingerprint          lowercase SHA-256 hex
result_appointment_version   positive integer
replacement_token_public_id  UUID string | null
```

The collection must not contain the raw token, customer email, customer phone, internal cancellation detail, or appointment notes.

### 5.2 Token indexes

1. Unique `{ public_id: 1 }`.
2. Unique `{ token_hash: 1 }`.
3. `{ tenant_id: 1, appointment_id: 1, purpose: 1, status: 1 }`.
4. Partial unique `{ tenant_id: 1, appointment_id: 1, purpose: 1 }` where `status="active"`.
5. TTL `{ purge_at: 1 }` with `expireAfterSeconds: 0`.

`purge_at` should be at least 90 days after the token becomes terminal so retry and incident evidence remains available.

### 5.3 Tenant self-service policy

Add to `tenants`:

```text
appointment_self_service
  enabled                    boolean, default false
  cancellation_cutoff_minutes integer, 0–10080
  reschedule_cutoff_minutes   integer, 0–10080
```

Platform-safe defaults when a value is absent:

```text
cancellation_cutoff_minutes = 1440
reschedule_cutoff_minutes   = 1440
```

### 5.4 Controlled service overrides

Add nullable service configuration:

```text
public_self_service_policy
  cancellation_cutoff_minutes integer | null, 0–10080
  reschedule_cutoff_minutes   integer | null, 0–10080
```

The precedence is:

```text
service override → tenant default → platform-safe default
```

These fields affect only public customer self-service. They do not alter Business Hub owner/admin correction authority.

### 5.5 Notification outbox extension

For confirmation and rescheduling notifications, store only the token reference required for deterministic link generation:

```text
appointment_access
  token_public_id            UUID string
  generation                 positive integer
```

Do not place the raw token or token hash in `template_data`.

## 6. Appointment eligibility and policy rules

### 6.1 Link issuance

Recommended PR 12 behavior: issue a management link for any newly scheduled appointment that has a deliverable customer email, regardless of whether staff or public booking created it.

Issuance requires:

- tenant self-service enabled;
- appointment status `scheduled`;
- a customer email snapshot available to the outbox workflow; and
- appointment start later than the effective token expiry floor.

No retroactive email or token backfill is performed. Existing appointments receive a token only after a future in-scope reschedule, if eligible.

### 6.2 Cancellation

Public cancellation requires:

- valid active token;
- appointment status `scheduled`;
- current time strictly before `starts_at - effective_cancellation_cutoff`; and
- exact confirmation text in the mutation payload.

The structured reason is always `customer_request`. PR 12 does not accept a public free-text cancellation detail.

### 6.3 Rescheduling

Public rescheduling requires:

- valid active token;
- appointment status `scheduled`;
- current time strictly before `starts_at - effective_reschedule_cutoff`;
- active tenant, service, provider, and provider-service assignment;
- a start returned by the existing deterministic engine; and
- no appointment conflict under the existing schedule-lock transaction.

`accepting_new_clients` does not block rescheduling an existing appointment. The customer cannot change the service, provider, customer, duration, buffers, price, currency, delivery mode, or operational snapshot.

The existing appointment is excluded from its own conflict check.

### 6.4 Cutoff boundary

Cutoffs are exact UTC instants derived from the appointment start. If `now` equals the cutoff instant, the action is no longer permitted.

## 7. Public API contract

All endpoints are hostname-scoped and require a valid `AppointmentToken` authorization header. No endpoint accepts a tenant ID.

### 7.1 View appointment

```http
GET /api/v1/public/appointments/manage/:token_public_id
```

Response:

```json
{

    "business": {
      "name": "Brazilian Wax Demo",
      "logo_url": null,
      "primary_color": "#1261A0",
      "phone": null,
      "email": null,
      "website": null
    },
    "appointment": {
      "reference": "BNT-E3A878EA",
      "status": "scheduled",
      "service_name": "Brazilian Wax",
      "duration_minutes": 30,
      "provider_name": "Lisa",
      "provider_photo_url": null,
      "starts_at": "2026-09-03T14:00:00.000Z",
      "ends_at": "2026-09-03T14:30:00.000Z",
      "local_start": "2026-09-03T10:00:00-04:00",
      "timezone": "America/New_York",
      "version": 1
    },
    "actions": {
      "can_reschedule": true,
      "can_cancel": true,
      "reschedule_until": "2026-09-02T14:00:00.000Z",
      "cancel_until": "2026-09-02T14:00:00.000Z"
    }
  }
}
```

Customer notes, internal notes, customer contact data, price internals, buffers, blocked intervals, audit data, user IDs, ObjectIds, and cancellation details are not returned.

### 7.2 Available replacement starts

```http
GET /api/v1/public/appointments/manage/:token_public_id/available-starts
  ?start_date=2026-09-05
  &end_date=2026-09-11
```

- Maximum inclusive range: 7 tenant-local dates.
- Reuses the existing provider/service scheduling engine.
- Applies the current tenant/service booking horizon and minimum lead policy.
- Excludes the current appointment from conflict evaluation.
- Returns the PR 9/10 public start DTO only; no blocked intervals or reasons.

### 7.3 Reschedule

```http
POST /api/v1/public/appointments/manage/:token_public_id/reschedule
Authorization: AppointmentToken <raw_token>
Idempotency-Key: <UUID>
Content-Type: application/json

{
  "expected_version": 1,
  "starts_at": "2026-09-05T15:00:00.000Z"
}
```

The first successful reschedule response returns the updated safe appointment DTO plus a one-time replacement management credential so the browser can continue the active self-service session. The credential is returned only in that successful response and is never persisted in browser storage. The replacement link is also delivered through the transactional rescheduling email. An idempotent replay returns the same business result without revealing the raw replacement credential again.

### 7.4 Cancel

```http
POST /api/v1/public/appointments/manage/:token_public_id/cancel
Authorization: AppointmentToken <raw_token>
Idempotency-Key: <UUID>
Content-Type: application/json

{
  "expected_version": 1,
  "confirmation": "CANCEL"
}
```

Successful response returns the safe cancelled appointment summary.

### 7.5 Idempotent mutation replay

The first successful mutation stores the idempotency-key hash, request fingerprint, result version, and replacement token reference on the consumed token record.

- Same key and same fingerprint: return the original successful result.
- Same key and different fingerprint: `409 idempotency_conflict`.
- Different key against a consumed token: safe `404`.

No new idempotency collection is introduced.

## 8. Transaction boundaries

### 8.1 Reschedule transaction

In one MongoDB transaction:

1. Resolve and verify hostname tenant.
2. Validate token hash, status, purpose, tenant, and expiry.
3. Revalidate appointment version, status, and cutoff.
4. Revalidate provider/service/assignment eligibility.
5. Acquire existing schedule-lock protection and recheck conflicts.
6. Update only the scheduled interval, timezone-derived fields, and appointment version.
7. Preserve all immutable service and operational snapshots.
8. Mark the old token consumed and record the idempotent mutation result.
9. Insert the next-generation token.
10. Insert the existing appointment-rescheduled audit event with public self-service source.
11. Insert the PR 11 rescheduling outbox notification containing the replacement token reference.

### 8.2 Cancellation transaction

In one MongoDB transaction:

1. Resolve and verify hostname tenant.
2. Validate token hash, status, purpose, tenant, and expiry.
3. Revalidate appointment version, status, and cutoff.
4. Apply the existing cancellation lifecycle with reason `customer_request`.
5. Consume the token and record the idempotent mutation result.
6. Insert the existing appointment-cancelled audit event with public self-service source.
7. Insert the PR 11 cancellation outbox notification.

No replacement token is issued after cancellation.

## 9. Safe errors

```text
404 appointment_not_found
409 appointment_version_conflict
409 appointment_time_unavailable
409 idempotency_conflict
422 cancellation_not_permitted
422 reschedule_not_permitted
422 validation_failed
429 rate_limit_exceeded
500 internal_error
```

Unknown token IDs, invalid raw tokens, wrong hostnames, cross-tenant tokens, disabled tenants, expired tokens, revoked tokens, consumed tokens, and terminal appointments all produce the same public `404` shape.

No endpoint reveals whether an appointment reference, email, customer, provider, or tenant exists. PR 12 adds no public lookup by appointment reference or email.

## 10. Security and abuse protection

- Reuse the bounded per-replica public limiter.
- Recommended limits per IP and token public ID:
  - 30 read requests per 10 minutes;
  - 10 mutation requests per 10 minutes.
- Reject malformed authorization headers before database mutation logic.
- Validate UUIDs and date ranges before collection queries.
- Do not include secrets, customer PII, token hashes, or raw tokens in logs.
- Sanitize and allowlist public response fields.
- Use `Cache-Control: no-store` for all appointment-management API responses.
- Require matching hostname tenant and token tenant on every request.
- Do not allow administrative sessions to substitute for the public token workflow.
- Do not add analytics to the management route.

## 11. Public UI

### 11.1 Route


### 11.2 Screen behavior

The page contains:

- tenant logo, business name, and safe contact information;
- appointment reference, service, provider, date, time, and timezone;
- action availability and plain-language cutoff information;
- reschedule flow: date → available time → confirmation;

- success state after each action; and
- a generic unavailable-link state.

The UI must not expose Business Hub navigation or administrative controls.

### 11.3 Credential handling

- Read the fragment once into in-memory application state.
- Remove the fragment from visible browser history using `history.replaceState` after capture.
- After a successful reschedule, replace the in-memory credential with the one-time replacement credential returned by the API.
- Safely update or remove the URL fragment so the superseded credential never remains in browser history; the replacement credential remains memory-only.
- Never persist the raw token in browser storage or cookies.
- Never render the raw token.
- A full refresh after fragment removal requires reopening the most recent appointment email link; document this expected security tradeoff in the UI if needed.

### 11.4 Accessibility and mobile

- Semantic headings, fieldsets, buttons, and confirmation dialogs.
- Visible keyboard focus and non-color selected states.
- Live announcements for loading, errors, available times, and successful actions.
- Large touch targets and no horizontal scrolling at 320px width.
- Date and time controls stack cleanly.
- Destructive cancellation requires explicit confirmation and is not the default focused action.

## 25. Decisions requiring approval

Implementation must not begin until these decisions are approved:

1. **PR 12 scope:** secure public appointment viewing, rescheduling, and cancellation—not reminders.
2. **Credential design:** purpose-bound token records with deterministic HMAC derivation, hash-only persistence, and one shared API/worker secret.
3. **Browser transport:** raw credential in the URL fragment and authorization header, never query parameters or storage.
4. **Lifecycle:** one active token per appointment, rotation on reschedule, consumption on cancellation, and 180-day maximum lifetime.
5. **Issuance:** links for all newly scheduled appointments with a customer email, including staff-created appointments, rather than public-booking appointments only.
6. **Cutoffs:** service override → tenant default → 24-hour platform default, with allowed range 0–168 hours.
7. **Hostname behavior:** reuse already verified public custom domains when resolved; otherwise use `tenant-slug.booknowtech.com`; no provisioning.
8. **Mutation retry:** store the terminal mutation replay result on the consumed token record rather than introducing a new idempotency collection.
9. **Rollout:** all tenants disabled by default and only the Brazilian Wax staging tenant enabled for PR 12 validation.

Any requested change to these decisions that affects an architectural invariant requires an ADR before implementation.
